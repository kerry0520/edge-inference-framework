# 文件换了位置，程序就变了吗

这一节区分两个问题：文件在哪里，以及它是不是那份已验过的文件。

从源码构建到手机运行，中间经过静态库、手机程序、构建记录与运行包。程序内容和它对应的验证证据决定了我们能作哪些承诺；目录只是读取这些输入的位置。

## 当前断点

现有构建配方能从明确的源码、补丁和工具输入开始编译，不需要旧库。但导出器还要求从作者历史目录读取三份验收记录，并照记录中的绝对路径寻找程序、库和冻结源码。别人移动同一份已验文件后，即使内容没变，也可能无法继续导出。

这不应通过删除哈希检查来解决。哈希用于核对实际字节，记录中的验收范围说明它在哪些设备、输入和配置上被检查过；取消这些约束，新的未验证程序也可能被误认作旧程序。

## 本次修改的职责

保留三份原始记录，不编辑它们写着的历史位置。另用一份位置映射告诉导出器：“现在到这里找程序、库和冻结源码。”读取后仍逐一比对原先固定的哈希和记录语义。

比如把`原目录/worker`放到`新目录/worker`，如果内容相同，位置变化不应使它失去身份；如果内容不同，即使文件名相同，也不能沿用原验收。路径检查还要拒绝意外逃出映射目录的相对路径和不符合约定的文件链接。

这只是让已有已验输入能搬移，不是自动验收新构建。新编出来的程序即使可以运行，仍需要自己的构建审查和手机验证，不能靠复制旧记录变成“已通过”。

## 和手机请求的关系

这些检查发生在启动手机程序之前。它们不计算token、不建立KV，也不改变MNN算子；职责是把应当执行的那份程序交给后续部署。离线检查通过不等于手机已执行，更不等于模型分数正确或速度更快。

本阶段已完成实现与独立审查：同一台电脑上的独立小客户端，在中文、空格新目录里解析6项真实输入成功，15次Python文件打开未访问旧历史路径；新旧默认入口结果完全一致。45项测试中44通过、1项旧环境符号链接权限跳过，另有6项独立小文件负例和已有真实Windows目录别名负例通过。

大程序与库采用只读硬链接验证，没有重复复制大文件或修改旧内容。没有真实导出另一份大运行包、编译、连接手机或运行模型；这也不是另一台电脑从零构建已通过。工程过程见续做记录（本地原件：`results/android/reproduction-contract-20261016/阶段续做.md`），理解待反馈。

## 新位置的显式输入

新增导出选项`--records-root`指向三份原字节验收记录所在的根目录；其下相对文件名仍固定为`build-review-v4/build-review.json`、`root-phone-acceptance-v1.json`和`recipe-v1/link-fix-v1/build.json`。`--source-build`应指向该根下最后一份文件。

`--artifact-map`指向独立JSON文件，且只接受下面三个键。相对路径从映射文件所在目录解释，禁止`..`逃逸；显式绝对路径也可使用，仍须通过原有哈希检查。新增映射路径不能经过符号链接或Windows目录重解析点；普通硬链接不改变字节身份，可以只读核验。

```json
{
  "binary": "资产/phone_chat_plan_worker",
  "library": "资产/libMNN.a",
  "source_inputs_directory": "资产/冻结源码"
}
```

```powershell
python scripts/android/phone_plan_profile.py export-source --source-build "搬移根/记录/recipe-v1/link-fix-v1/build.json" --records-root "搬移根/记录" --artifact-map "搬移根/位置映射.json" --output "新的运行包目录"
```

该导出不编译、不部署、不含模型权重；需要已经具备且身份符合要求的真实记录和文件。新clone只有代码，仍不能凭空生成旧验收证据。输出目录必须全新，失败时保留已有内容。未提供新增选项时继续使用原入口及其既有验收约束。

旧默认入口保留历史已验目录别名兼容；新增显式映射才采用严格的祖先链接检查。这是接口兼容要求，并非降低新路径的检查。实际Windows目录别名常常不是`is_symlink()`所能识别的普通符号链接，本轮用`lstat()`确认重解析属性，真实负例被正确拒绝。
