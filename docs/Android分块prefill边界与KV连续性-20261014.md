# 为什么“满块”不等于“中间块”

## 希望你理解什么

分块 prefill 的每一块都要更新 Transformer 的各层 KV，但只有一段输入的最后一块需要交付用于采样的词表分数。是否最后一块由输入进度决定，与块的大小没有必然关系。

你在 nano-vLLM 中学过分块，这里沿用这个概念，补上 MNN 的具体职责：主干 Module 计算 hidden_states 并更新 Attention 的 KV；完整 Module 在此之后继续归一化和词表投影，输出下一 token 的 logits。

## 用长度直接看职责

本轮固定最大块长32。

| 输入长度 | 分块 | 候选执行路径 |
| --- | --- | --- |
| 31 | 31 | 完整模型 |
| 32 | 32 | 完整模型 |
| 33 | 32＋1 | 主干→完整模型 |
| 64 | 32＋32 | 主干→完整模型 |
| 65 | 32＋32＋1 | 主干→主干→完整模型 |

如果写成“块长小于32才是最后块”，64这个例子就坏了：两块都是32，你会省掉本来要拿来采样的最后词表输出。正确判断是“处理完这个块后，还有没有待处理输入”。

别把最后1-token prefill误当成decode。33的第二块虽然只有1个token，却仍属于输入处理；其后，送入一个已选token再预测下一个，才是decode。本轮程序显式标注阶段，不通过形状猜。

## 切换计划时，历史必须连续

假设先输入64个token，然后处理1个decode token，再继续输入33个token。历史长度应该是：

`32 → 64 → 65 → 97 → 98 → 99`

前两个数是首段prefill；65是decode之后；97和98是新增33个token分成32＋1后的结果；99是第二次decode之后。新增输入的position应该从65开始，不能从0开始。

主干计划和完整计划虽然是不同Module，同一层Attention必须接着使用同一份KV。否则每个程序片段看起来都能执行，后续logits却依据错误的历史。相反，如果同一块被重复追加，历史又会多长一截。因此本轮逐层核对28个manager的身份与长度，也核对position和共享meta，而不只看回答是否像正常文字。

这里继续输入的是预先固定的token ID。它可以验证底层KV连续性，但没有经过消息模板、聊天历史提交和正式生成循环，所以不能称为正式多轮聊天已经验收。

## 怎样判断这一层验证完成

需要同时看到：中间块head没有执行；最后prefill和decode仍执行head；所有Attention各处理一次，KV长度与position连续；新旧路径交付的完整词表分数都有效且一致。少一项，都不足以证明这个执行计划可靠。

这也还不能给出速度提升。减少head调用是减少工作量的证据，最终用户等待时间还受加载、输入处理、主干计算、生成与传输影响。下一层应接入正式response，再用没有逐层观测日志的版本做性能对照。
