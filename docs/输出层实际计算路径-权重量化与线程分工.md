# 输出层实际计算路径：权重量化与线程分工

这次希望你能把四件事串起来：输出层算什么、权重怎样保存、框架实际选了哪个计算入口、任务怎样分给线程。以下是固定Mi11/0.6B/CPU4、同库隔离观测的结果，不代表所有MNN模型。

## 从一个token的位置开始

decode当前只有一个位置，它已经得到1024维隐藏向量。输出层要给151,936个候选token打分；每个候选对应一行权重，分别与这个向量计算，最后得到151,936个分数。

因此可以按候选行分任务：本次实际观察到4个逻辑任务，每个负责37,984行，四段首尾相接且没有重叠。大家读同一份输入，计算不同候选的输出。这是输出通道分工，不是把4个token同时生成，也不证明四个任务固定在四个物理核上。

## 16个量化块和4个任务是两回事

本次输出层解码资源记录为8位、非对称量化、16个权重块；对应1024输入维度，逻辑上每个块64维。每块使用对应的量化参数，部分计算结果经过对应缩放、补偿和累加，才得到候选的最终分数。块是量化组织，任务是并行工作安排，不能把16个块理解为16个线程。

此前只读文件确认的是8位编码；这次从实际执行器资源确认`origin_bits=8`、`weight_bits=8`、`can_use_int4=0`，证据层次不同。还记录到`dynamic_quant=1`、`input_block_num=1`，说明走了该执行器的动态量化配置；仅凭这些字段不展开推断所有输入量化细节。

## 真正选中的函数

在实际调用点记录选中指针，减去本进程模块基址，再匹配本次冻结ELF的函数符号，得到：

`MNNGemmInt8AddBiasScale_ARMV82_Unit_FP16`

它是实际传入调用的函数，不是后端函数表中“可能可用”的一个候选。观察到的core存储宽度是2字节、pack为8。函数名和这些字段不能被简化成“权重变成FP16”或“所有运算都用FP16”；存储、乘加计算、缩放补偿、输出格式是不同层次。若要解释具体指令，仍要读取对应函数实现。

## 为什么先验证结果

隔离观测只替换一个卷积归档成员，正式库不改；类布局、原算术和工作范围不改。原库参考与观测程序均关闭debug，用同样32个输入ID、32生成预算，各一个进程，预热和正式各一题。完整逐forward logits、生成结果和记录状态一致后，才解释元信息。

观测仍有锁和去重开销，因此本次不比较两程序快慢，也不把此前30.01%的热点比例当成这批的新测量。当前只确认执行路径，尚未获得新的提速。

## 接下来应解决哪个问题

现在已知道实际函数和分工，下一步只评估这个精确路径中可改善的成本。仍不能仅凭权重大就宣布访存瓶颈，也不能凭“4个任务”认定调度最优。若要分解输入准备、GEMM和后处理，必须同轮对齐边界，不能把并行线程时间直接相加或借用旧版本的耗时。

独立原件复核2646项及协议7项实际通过。详细设备记录、ELF、完整logits与原始会话留在原工程，不随公开仓库分发；本材料已提供不等于学习者已掌握。
