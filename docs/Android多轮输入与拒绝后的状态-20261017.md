# 多轮输入与拒绝后的状态

本节只抓一件事：**模型下一次看到什么，取决于应用提交了哪些历史。**

## 短问题为什么也可能有长输入

当前完整重算模式下，应用会把已确认历史和新问题一起套聊天模板，再交给Tokenizer。假设你先问A，模型答A，再追问B，下一次输入包含A、答A和B，不只是B。随后说“请简短总结”，模型仍需看到前面的对话。

这条链是：会话历史＋新问题→聊天模板→token ID→prefill/decode→新回答。已有nano-vLLM基础可以直接衔接：本模式reuse_kv=false，每轮仍重新计算完整输入；执行计划复用省准备工作，不等于复用旧上下文计算。

## 超预算请求应该停在哪里

模板和分词后，实际输入加生成预算若超过部署预算，这一轮会拒绝。这里的512是本入口部署预算，不是模型固有最大上下文。

拒绝记录可以保存，已确认历史却不能追加这条用户消息，更不能追加一个不存在的模型回答。此前的历史、已有计划状态、上一条成功统计和成功请求列表都应保持。下一题从拒绝前的状态继续，才能得到正确输入。

例如A和B已完成，C过长被拒绝，之后问D：D应看到A/答A/B/答B/D，不能包含C。new是另一种操作：你主动放弃之前历史，让下一题从空对话开始；适用的执行计划仍可保留。

## 本轮如何把概念接到真实项目

新包先前只验独立题，本轮用同一进程检查连续追问、超预算拒绝、拒绝后继续、新对话和短长切换。拒绝前后的状态单独保存，生成token和文字还与旧源码包同场景原件对照。原件比较不看耗时，不据此给新程序提速结论。

源码沿职责读即可：`phone_chat_session.py::ask()`先形成messages并处理预算拒绝，成功final验证后才更新history；`new()`清历史；`phone_chat_plan.py::ask()`在成功请求提交后更新计划状态。最后才是LLM将token交给MNN图执行与CPU算子。

本轮结果见阶段记录（作者本地工程原件）。本节已提供解释，理解待反馈。

## 再往下接一层真实MNN源码

电脑端提交messages后，手机worker的`budget()`先调用MNN的`Llm::apply_chat_template()`与`tokenizer_encode()`，得到真实token数量。预算不够就发送rejected并继续等下一题，没有进入`infer()`。成功路径才调用`llm->response(messages, ...)`，随后由LLM安排prefill/decode。

worker还维护已确认messages前缀，下一题必须接在这个前缀后；成功回答后才更新committed列表。这样电脑历史与手机已确认前缀相互核对，避免两端各自以为对话进度不同。

固定版本入口：项目`apps/android/phone_chat_plan_worker.cpp`的`budget()`和serve循环；MNN `transformers/llm/engine/src/llm.cpp`的`Llm::response(const ChatMessages&, ...)`。本轮实编源码在本地固定source目录；先看职责关系，不要求逐行读模板或JSON处理。

本轮工程已完成。一个具体例子是“请简短总结”：实际输入为103token，因为messages里还含前两轮已确认对话和模板，不能按这几个汉字估算prefill输入。超长题被拒绝后，这份历史保持原样；随后new再主动清空。五题生成轨迹与旧包一致，退出清理通过。本轮不评价8token片段的任务质量，也没有新增性能结论。

## 为什么每题reset，模型仍能接上前文

这里最容易混淆的是两个“历史”：应用的消息列表，与MNN内部本次计算的token/序列状态。它们不在同一个对象里。

Python的ask()先把已确认消息与新问题拼成messages；手机收到后核对它是否接在已确认前缀后。在infer()里，llm->reset()重置MNN这次生成相关的状态，然后response(messages, ...)重新处理完整messages。reset没有清掉Python已经拼好的列表，也没有把传入的文字删除。因此，重置内部状态与保留对话上下文完全可以同时成立。

用已知例子对应源码：

```text
电脑历史：[用户：暗号是蓝风铃，助手：已确认]
新问题：暗号是什么？
发给手机：[用户：暗号是蓝风铃，助手：已确认，用户：暗号是什么？]
手机：reset本次计算状态 → 重新计算上述完整输入 → 生成新回答
成功final核验后：电脑历史再追加本次用户/助手两条消息
```

这不是说每次重新加载模型。模型对象和权重仍驻留；重置的是适用的请求状态。也不是说每次把所有KV内存都释放：KV内容是否作为旧前缀继续使用，与底层是否保留已分配缓冲区，是两个问题。当前固定路径reuse_kv=false，不把上一轮KV内容作为这轮已完成的计算复用。

| 状态 | 谁持有、存什么 | 成功问答 | 预算拒绝 | /new |
| --- | --- | --- | --- | --- |
| 已确认消息 | Python history、worker committed；用户/助手文字 | 追加两条 | 不追加 | 清空 |
| 本次计算状态 | MNN context/meta；token、序列、生成状态等 | 当前请求更新 | budget在infer前拒绝，不执行这题的模型计算 | 调用reset；后续输入从新消息开始 |
| 适用执行计划 | 绑定到模型/运行时的Module与执行准备 | 合法条件下准备或复用 | 不因未执行题目提交新回答 | 不随消息列表直接清除；仍须核对绑定有效 |

不要把前一轮残留的内部计数当成下一轮有效上下文；真正进入infer时仍有reset和当前reuse_kv配置约束。表中“计划保留”也不是任意形状/任意模型都能命中，短输入可退回完整路径。

### 按职责读源码，不要一次打开全部文件

1. `scripts/android/phone_chat_session.py`的ask：找到messages构造，再找到验证成功后self.history赋值。中间的rejected分支会提前抛出可恢复的预算异常。
2. `apps/android/phone_chat_plan_worker.cpp`的serve循环：先核committed前缀，再budget，最后infer；只有infer成功才更新committed。/new分支清committed并reset。
3. 同文件infer：先reset，再response(messages)。这两句连起来解释上面的疑问。
4. 固定MNN `transformers/llm/engine/src/llm.cpp`的Llm::reset、generate_init和response(ChatMessages)：这是应用消息变成MNN计算的接口；不要把Python列表当作MNN内部缓存。
5. `apps/android/prefill_trunk_reuse.hpp`的owners/cached/bound：这是另一份计划状态，检查身份绑定后才能复用，与历史文字不是同一份数据。

这些入口对应当前固定版本；先能解释“消息在哪里”“重置了什么”“拒绝停在哪”，再读具体算子。下面是新编程序的本轮结果；前面2026-10-17的实机结论仍只属于当时程序。

## 新编程序的真实连续对话（2026-10-18）

同一份新编worker完成了下面的过程；这四条成功回答发生在同一个驻留模型进程里：

| 操作 | 手机收到的消息 | 实际结果 |
| --- | --- | --- |
| 告诉模型暗号是蓝风铃 | 这条用户消息 | 好的，已记好暗号。 |
| 问暗号是什么 | 第一轮用户/助手＋本题，共3条 | 蓝风铃。 |
| 发送过长输入 | 准备提交的完整历史＋过长题 | 拒绝；不追加历史、不进入本题infer |
| 再问一次暗号 | 原已确认的两轮＋本题，共5条；没有被拒题 | 蓝风铃。 |
| /new后问一句介绍 | 只含这条新问题，共1条 | 你好！我是AI助手，随时为您提供帮助。 |

实际输入token从30到60、86，new后回到19。这与消息历史逐渐增加、清空后重新开始一致；不能按最后一句问题字数估输入成本。被拒题实际2174输入token加24生成预算，超过本入口512预算。它没有产生回答，也没有出现在之后的messages里。

验收检查的是原始messages前缀、成功提交、拒绝不提交和new后的边界，而不是只看模型恰好答出了暗号。/new后没有继续追问旧暗号，因此不作“模型绝不可能猜到旧暗号”的语义断言；这里证实的是程序没有把旧messages再次传入。计划命中不等于KV命中，更不等于答案缓存。

工程结果压缩为一句：新候选四题、拒绝后继续、清历史、流式原件及退出清理通过独立核对，模型文件未改，候选状态保留；首次连接前失败原件保留。见[新程序多轮验收](../evidence/new-candidate-state-20261018/README.md)。本轮没有测速度、完整数值等价或通用任务质量。理解状态仍待你的复述或问题。
