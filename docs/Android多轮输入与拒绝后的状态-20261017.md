# 多轮输入与拒绝后的状态

本节只抓一件事：**模型下一次看到什么，取决于应用提交了哪些历史。**

## 短问题为什么也可能有长输入

当前完整重算模式下，应用会把已确认历史和新问题一起套聊天模板，再交给Tokenizer。假设你先问A，模型答A，再追问B，下一次输入包含A、答A和B，不只是B。随后说“请简短总结”，模型仍需看到前面的对话。

这条链是：会话历史＋新问题→聊天模板→token ID→prefill/decode→新回答。已有nano-vLLM基础可以直接衔接：本模式reuse_kv=false，每轮仍重新计算完整输入；执行计划复用省准备工作，不等于复用旧上下文计算。

## 超预算请求应该停在哪里

模板和分词后，实际输入加生成预算若超过部署预算，这一轮会拒绝。这里的512是本入口部署预算，不是模型固有最大上下文。

拒绝记录可以保存，已确认历史却不能追加这条用户消息，更不能追加一个不存在的模型回答。此前的历史、已有计划状态、上一条成功统计和成功请求列表都应保持。下一题从拒绝前的状态继续，才能得到正确输入。

例如A和B已完成，C过长被拒绝，之后问D：D应看到A/答A/B/答B/D，不能包含C。new是另一种操作：你主动放弃之前历史，让下一题从空对话开始；适用的执行计划仍可保留。

## 本轮如何把概念接到真实项目

新包先前只验独立题，本轮用同一进程检查连续追问、超预算拒绝、拒绝后继续、新对话和短长切换。拒绝前后的状态单独保存，生成token和文字还与旧源码包同场景原件对照。原件比较不看耗时，不据此给新程序提速结论。

源码沿职责读即可：`phone_chat_session.py::ask()`先形成messages并处理预算拒绝，成功final验证后才更新history；`new()`清历史；`phone_chat_plan.py::ask()`在成功请求提交后更新计划状态。最后才是LLM将token交给MNN图执行与CPU算子。

本轮结果见阶段记录（本地原件：`results/android/fresh-lifecycle-acceptance-20261017/阶段续做.md`）。本节已提供解释，理解待反馈。

## 再往下接一层真实MNN源码

电脑端提交messages后，手机worker的`budget()`先调用MNN的`Llm::apply_chat_template()`与`tokenizer_encode()`，得到真实token数量。预算不够就发送rejected并继续等下一题，没有进入`infer()`。成功路径才调用`llm->response(messages, ...)`，随后由LLM安排prefill/decode。

worker还维护已确认messages前缀，下一题必须接在这个前缀后；成功回答后才更新committed列表。这样电脑历史与手机已确认前缀相互核对，避免两端各自以为对话进度不同。

固定版本入口：项目`apps/android/phone_chat_plan_worker.cpp`的`budget()`和serve循环；MNN `transformers/llm/engine/src/llm.cpp`的`Llm::response(const ChatMessages&, ...)`。本轮实编源码在本地固定source目录；先看职责关系，不要求逐行读模板或JSON处理。

本轮工程已完成。一个具体例子是“请简短总结”：实际输入为103token，因为messages里还含前两轮已确认对话和模板，不能按这几个汉字估算prefill输入。超长题被拒绝后，这份历史保持原样；随后new再主动清空。五题生成轨迹与旧包一致，退出清理通过。本轮不评价8token片段的任务质量，也没有新增性能结论。
