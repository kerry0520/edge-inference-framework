# 一次实机回答怎样对应到被测程序

这节只抓住一个问题：**看到回答正确以后，怎样确认它来自我们正在验证的那份程序？**

你熟悉 prefill、decode 和 KV cache。这里没有增加一种推理算法，而是在把这些步骤变成可以交付、可以复查的工程结果。

## 从请求到证据

一次请求有几组输入：程序和库、模型文件、运行配置、问题的 token。程序执行后，产生输出 token、执行路径和进程日志。验收必须把两端连起来：哪份程序在什么配置下，实际接收了什么，给出了什么。

例如，两份 worker 都能回答同一道加法。仅比较答案，无法判断新 worker 是否真的被部署。需要同时核对候选清单中的程序摘要、会话记录的部署摘要、手机侧保存的程序摘要，并把日志中的会话 ID 和进程身份接上。只比较答案会漏掉“仍在运行旧程序”这类问题。

## 为什么不能只看 passed

`passed: true` 是检查器的结论。复查时应回到原始输入和输出，重新算结论：输入 token 是否符合固定参考；输出 token 签名是否一致；重置之后是否用了新上下文；记录的执行路径和缓存命中是否符合约定；退出和清理记录是否相互一致。

把结论再复制一次，不算独立复查。把原件固定下来，然后重新执行检查逻辑，才可以发现“原始记录与总结矛盾”。本轮工具仍复用项目检查逻辑，因此也不能把它说成来自另一套独立实现的算法证明。

## 离线重算负责什么

手机负责真实执行；电脑上的重算器只读取此前保存的证据。根清单记录文件的大小和 SHA256，外部给定的根清单摘要固定了这套字节。重算器先检查文件有没有变化，再检查这些文件表达的事实是否一致。

所以，改了原件会被摘要检查拒绝；即便重新计算摘要，把明显矛盾的进程身份或输出记录封装进新清单，也应被语义检查拒绝。

摘要并不证明记录是谁写的，也不能证明历史日志没有被整体伪造。离线重算更不意味着手机现在在线，或现在没有残留进程。

## 与主线的关系

主线仍是：文字 → token → prefill/decode → MNN 执行 → 输出。这里增加的是贯穿这条链的身份核对。它让将来的改动能回答：这次结果是否真的来自这次改动，是否有足够记录供别人复查。

候选验证通过也不会自动进入正式运行包。候选状态、设备证据和正式准入是三件事；当前工具保留 `candidate_pending` 与 `production_admitted: false`，正式会话检查器仍限制已有登记身份。

## 本轮范围

工程结果在完成实际核对后追加于此。历史清理记录没有独立时间戳，因此只能检查记录集合和会话声明一致，不能证明清理操作的严格先后顺序。短回答用固定 token 截断作回归信号，也不等于回答质量评测。没有新增模型运行、性能结论或 Metal/GPU 验证。

源码入口：`scripts/android/phone_candidate_validation.py` 负责实际候选验证；`phone_candidate_validation_replay.py` 负责固定证据与离线重算；`phone_verify_session.py` 提供会话语义检查。你无需先背清单字段，先理解“程序、输入、输出必须属于同一次被测执行”。

## 已完成的工程结果

两套历史实机记录已分别固定原件并通过离线重算，每套三次请求、两次重置和11条清理原件互相一致，53份历史元数据/日志均未修改。错误外部摘要被拒绝；只改派生执行数并重新计算根摘要，也因重算矛盾被拒绝。34项新增测试与11项原正式会话验收测试通过。没有重新运行手机模型；原正式身份限制和候选待验状态保持。

原始证据与续做（作者本地工程原件）保留命令退出码、测试计数、限制及采集失败记录。学习者是否理解仍待你反馈，工程通过不等于已掌握。
