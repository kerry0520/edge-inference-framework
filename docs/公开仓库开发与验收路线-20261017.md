# 公开仓库：能独立做到哪一步

这份路线面向准备阅读、修改和复现项目的人。当前公开代码可以离线测试、按固定配方构建、生成待验候选并核查构建来源。正式运行包仍只登记已独立审查的固定程序，外部新编产物不会自动获得正式身份。

## 从哪里开始

先在公开仓库根目录运行：

```powershell
$env:PYTHONUTF8 = "1"
python -B -m unittest discover -s tests/android -p "test_*.py" -v
```

这些是客户端协议、状态、打包和构建配方的fixture/mock测试，不需要模型、手机、ADB或NDK。个别测试会启动本机Python短子进程模拟失败；没有真实编译模型。测试报告应核对实际退出码和非零执行数量；skip表示该项未执行。公开仓库的GitHub Actions按Python3.11分别在Windows与Linux运行这条命令；远端状态需看实际运行结果，配置文件存在不等于通过。

自动测试不是新的推理功能。它保护的是已有约定：例如请求未确认时不能提交历史、运行包文件损坏时不能继续选择、构建记录不能把失败当成功。真实算子输出、模型数值及手机性能仍需设备验证。

CI显式启用UTF-8，并使用runner提供的临时目录。首轮Windows默认cp1252无法处理部分中文测试数据，系统TEMP的8.3短路径又与解析后的长路径拼写不同，触发fixture中的路径比较及mock失配；首轮失败原件保留。当前配置不证明未配置的cp1252重定向输出或混用长短路径已经通用适配，也不通过跳过断言来制造通过。

后续已单独修复候选生成/复查回传路径拼写不一致的问题，并用真实8.3别名的合成资产对照；见[候选路径一致性](候选路径一致性修复-20261018.md)。这不改变清单内容、待验状态或设备准入，也不等于所有Windows路径及编码差异都已解决。

## 构建、候选、验收、正式包分别意味着什么

| 阶段 | 输入与输出 | 当前能证明什么 |
|---|---|---|
| 固定配方构建 | 固定MNN提交、补丁、NDK等→库、手机程序与构建记录 | 确实生成程序，不能单凭编译成功证明计算正确 |
| 候选清单与构建审查 | 新程序及实际记录→待验绑定、审查报告 | 文件与来源对应；候选仍待验 |
| 设备实验 | 候选＋独立输出参考＋固定手机模型→逐题对照 | 这些输入上的结果与参考相同，不是全部输入都正确 |
| 正式运行包 | 已完成审查并明确登记的程序→profile及可启动包 | 当前程序可以被正式客户端选择；没有任意新程序自动准入 |

构建按[固定配方](../configs/android/mnn-source-build/README.md)准备外部依赖；再看[待验候选](Android新构建的待验候选-20261016.md)、[构建审查](离线源码构建审查入口-20261017.md)。目前 `export-fresh` 还要求作者固定验收原件和已登记程序摘要，公开仓库未分发那些原件或程序。不要把新构建记录填进旧命令，或修改摘要白名单来绕过审查。新电脑从零构建到正式包的独立复现仍未完成。

## 固定输出参考现在放在哪里

公开文件为 `configs/android/candidate-reference-mi11-qwen3-06b.json`，SHA256固定为：

```text
c8236e64cdddaf7fbea8e70503d6a5b82d7174496cd380fec56a8a1f2f348c3b
```

它是既有独立受验程序的两道人工题参考，保留原字节；不是新候选运行后生成的答案。文件包含五个模型文件的SHA、CPU配置、提示词、完整输入/输出token ID、文字、结束状态和流字节摘要，没有权重、程序或原始设备日志。其本地来源是候选设备验证阶段保存的reference，真实调用证据仍保存在作者工程档案，公开摘要不代替原件。

这个参考固定CPU四线程、greedy、chunk32与当时配置；每题只生成4token。短题的“2 + 1”是截断输出，不用于证明算术回答正确。它覆盖两组输入，不能替代完整logits比较或稳定性能验证。

`phone_candidate_validation.py` 的离线命令格式如下，占位SHA需换成你已绑定的实际候选SHA，输出目录必须是新的：

```powershell
python -B scripts/android/phone_candidate_validation.py --candidate candidate.json --expected-candidate-sha256 "实际候选SHA" --reference configs/android/candidate-reference-mi11-qwen3-06b.json --expected-reference-sha256 c8236e64cdddaf7fbea8e70503d6a5b82d7174496cd380fec56a8a1f2f348c3b --output "新的检查目录"
```

默认只核输入；增加 `--run` 才会部署并执行三次请求。**设备链还固定硬件序列号 `1e7c759e`，同为Mi11/M2011K2C也不自动通过。** 发布参考没有解除设备限制，也没有创建通用回归基准。其他设备需要明确配置、独立参考和新的验收，本轮未实现该扩展。

## 你应理解的工程原理

最重要的是“候选不能用自己产生的答案证明自己正确”。先前可信程序的结果与新候选结果分别保存，再在相同输入、模型和配置下比较，才有对照意义。例如两份程序都返回“你好”只核对了一个现象；检查完整token、文字、状态和流数据可以多排除一些协议错误，但仍不代表所有模型输出相同。

这条工程线位于真实请求主线之外，负责检查改动是否值得交付。计算本身仍是消息→token→prefill/decode→MNN图执行→CPU算子→采样。读框架时先理解这条计算链，需要修改并交付时再用本页的验收路线。

工作流使用官方[checkout](https://github.com/actions/checkout)和[setup-python](https://github.com/actions/setup-python)，固定具体提交；只读仓库权限，不申请设备、模型或项目密钥。远端运行状态与本轮结果另见项目交付说明。
