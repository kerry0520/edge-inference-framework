# 当前运行包：怎样检查一次请求真正做了什么

这次补齐的是记录检查器：已正式登记的三版程序应能用同一入口检查。fresh版此前能运行，但检查器漏了它的身份，导致正常记录被误拒；本轮只补该固定身份，不让未知候选自动成为正式程序。

## 看记录时抓住一条计算线

消息先变为token，LLM安排prefill/decode，再调用MNN模型图。我们启用的可选路径会把prefill按32个token分块：非最后一块只需要为后面留下上下文，不必每次都投影到整个词表；最后一块仍产生分数以继续生成。

例如126个输入token分成32、32、32、30四块。前三块走主干，最后一块走完整模型。之后decode也需要完整模型的分数。注意，这不是删掉前三块的Transformer或Attention，也不是跳过它们的上下文计算；省掉的是那些位置不需要的词表输出部分。

## 三个计数不要重复相加

| 记录 | 含义 |
|---|---|
| `trunk_count` | 本次请求只执行主干的次数 |
| `full_count` | 本次请求执行完整模型的次数，已包含decode |
| `decode_count` | 上面完整模型次数中属于decode的部分 |

例如记录若为trunk3、full5、decode4，总执行次数是3+5=8，而不是3+5+4。完整模型的5次中，1次来自最后prefill块，4次属于该记录的decode调用。不要只凭生成token数猜所有调用次数，应结合结束状态和真实执行记录。

主干执行计划缓存保存“怎样准备和执行图”，不保存上一题的答案。`/new`清对话后仍可能复用准备好的计划，但新输入的模型计算仍要进行。这与跨轮复用已算好的KV是不同的省时来源。

检查器会核token与消息历史、流式分块与最终文字、计数关系、模型文件前后、进程退出和清理记录。所以它不只是搜索一行“运行成功”。本次固定身份扩展以后，fresh记录也要满足这些原有规则。

## 离线检查怎样使用

准备同一次已有正式CLI运行的三份原件：session JSON、手机worker原始stdout，以及真实CLI的命令/退出记录。在项目根目录运行，替换实际路径，输出文件必须不存在：

```powershell
python -B scripts/android/phone_verify_session.py --session "session.json" --worker-stdout "worker-stdout.log" --cli-command "真实CLI-command.json" --output "新的检查结果.json"
```

记录包含原生预算拒绝时，可加 `--allow-budget-rejections`，仍会检查拒绝帧与已确认历史。API场景驱动器的退出不能直接冒充正式CLI退出；只有collector成功也不能说明worker成功。

源码入口：[离线检查器](../scripts/android/phone_verify_session.py)、[手机worker](../apps/android/phone_chat_plan_worker.cpp)、[主干执行辅助代码](../apps/android/prefill_trunk_reuse.hpp)。本轮实际输入和旧新检查器结果见工程记录（本地工程原件）。

## 通过以后能说什么

通过只说明这些原始记录内部一致，并能归到已登记程序；不自动认证日志来自独立第三方，不证明所有模型输入正确，也不表示此刻手机仍在线。重读旧记录不是新跑模型，不应新增性能数字。

未知新构建仍要自己的来源审查、设备验证和明确登记。显式候选聊天入口本轮尚未实施，不能凭自己写一个`passed=true`就接入。你这次应理解的是执行路径和计数如何对应；工程已经通过不等于你已经掌握，理解待反馈。
