# 从公开源码生成新的手机程序

这节只理解一个区别：**工具和源码是构建的输入，旧对象与旧库是上一次构建的输出。** 换目录运行旧程序只能说明程序能搬动；从公开源码和明确依赖重新编出程序，才能检验别人是否能继续开发这个项目。

## 各种文件在做什么

| 文件 | 职责 | 这轮能否复用 |
| --- | --- | --- |
| 固定提交的MNN源码、项目补丁、worker源码 | 描述要执行什么计算与协议 | 作为明确输入读取 |
| NDK、CMake、Ninja、锁定的KleidiAI压缩包 | 编译工具和外部依赖 | 作为明确输入使用 |
| `.o`对象、`libMNN.a`、worker程序 | 编译与链接产生的结果 | 新构建不复用旧结果 |
| 模型权重 | 程序运行时加载的数据 | 不参与编译，本轮不重新下载或修改 |

`libMNN.a`里有框架实现，手机worker把请求协议接到MNN。完整编译得到框架库，再链接worker，才得到可以放到手机执行的程序。这不是把模型权重“编进”程序。

## 为什么还需要一个小采集入口

验证器会保存题目、模型输出和资源清理，但它结束以后才能知道操作系统给它的真实退出码。因此需要父进程启动验证器，把这次命令、标准输出、标准错误和真实退出码保存下来。

原来这一步在本机实验脚本里，公开用户就接不上后面的证据封装。新增的`phone_candidate_validation_collect.py`只把这一小步公开，仍调用原验证器，不增加另一套验证协议，也不把`passed: true`当成操作系统退出码。

默认只检查输入和生成计划；明确`--run`才运行一次设备验证，不自动重发请求。输出目录每次新建。子进程使用英文临时目录和UTF-8，不修改系统环境。若启动失败或中断、实际退出未知，就如实留下未知记录，不能封装成成功，也不能宣称手机资源已经清理。

## 从构建到回答的顺序

1. `build_mnn_source.py prepare`：从固定Git提交导出源码、应用补丁，准备依赖及命令；还没有编译。
2. `build`：从空对象目录完整编译和链接，产生新库、新worker及构建记录。
3. `phone_source_candidate.py prepare`：绑定这次产物，保留待验状态。
4. `phone_source_build_audit.py`：检查构建输入、实际命令与产物对应。
5. 新采集入口调用设备验证器：保存真实执行和父进程退出原件。
6. `phone_candidate_validation_replay.py seal/replay`：固定并重算这次设备记录。
7. `phone_candidate_chat.py --run`：用这份新候选接受新问题，仍明确不是正式准入。

这条链负责让改动可以交付。模型执行主线仍是消息→token→prefill/decode→图执行与算子→采样，不需要把每一种记录文件当成推理算法学习。

## 本轮结果与边界

已从干净公开代码副本重新导出源码，在空对象目录完整生成565个对象和565成员框架库，链接出新worker；没有复用旧对象或旧库。新候选的构建审查、公开采集器真实手机三题、设备原件封装与离线重算都已通过。第一次CMake试编对象写入被拒的目录保留，另一次新对象目录构建成功；没有改源码、权限或手工补链接命令。

这使用的是同一台电脑上已有的明确工具和依赖；不能因此说另一台电脑、不同工具版本或其他手机已经通过。新程序仍为候选，三题各4token只做限定轨迹对照，不是完整答案质量或性能结论。这份新候选随后完成一次真实新问题，回答“你好！我是AI助手，随时为您提供帮助。”；父进程、原生退出与资源清理均核对通过。仅证明这次单题链路，不借用旧fresh候选的多轮或完整数值结果。

构建的完整说明见[固定配方](../configs/android/mnn-source-build/README.md)，候选运行职责见[从新构建到试用](从新构建到候选试用-20261018.md)。已讲不等于已掌握，先能分清输入与产物即可。

## 新采集入口怎样使用

候选文件应来自这次构建；参考使用公开的固定两题文件。下面文件路径和候选摘要须替换，输出必须是尚不存在的新目录：

```powershell
python scripts/android/phone_candidate_validation_collect.py `
  --candidate candidate.json --expected-candidate-sha256 CANDIDATE_SHA `
  --reference configs/android/candidate-reference-mi11-qwen3-06b.json `
  --expected-reference-sha256 c8236e64cdddaf7fbea8e70503d6a5b82d7174496cd380fec56a8a1f2f348c3b `
  --output C:\edge-work\validation-plan
```

默认命令只有离线检查。设备执行时用另一个新输出目录，再加`--run`；需要时显式提供`--adb-path`和当前`--serial`。完整限定设备条件见[公开验收路线](公开仓库开发与验收路线-20261017.md)，不同硬件序列号不会自动通过。

**采集器自身退出码也必须为0，才能继续封装。** 它的子进程可能退出0，但采集后的输入复核失败。采集器会保留那个真实子进程0，同时自己返回失败；不要只读`collector-command.json`里的子进程值就忽略外层失败。

成功执行的根目录包含`run/`和四份`collector-*`原件。后续seal使用`--run-dir 根目录/run --cli-command 根目录/collector-command.json`及实际计算并审定的CLI文件SHA，其他candidate/reference及pin保持一致。seal输出须在采集器根目录之外的新兄弟目录；replay再用另外的新目录。旧验证器、seal协议和正式白名单都未改。

新入口23项测试通过；已有真实候选的默认CLI在禁用进程启动的检查下退出0、启动尝试0、没有伪造child命令或run目录。这仅验证默认离线路径，不是本轮新构建或设备执行成功。

## 连续操作例子（Windows）

先准备固定提交的MNN Git仓库、完整NDKr30、CMake、Ninja、锁定KleidiAI压缩包和已配对的目标手机。下面是操作模板，所有`待替换`值必须替换；在公开仓库根目录执行。`$w`要选新的、无空格的英文路径。它不是一键安装，不下载依赖，不改变正式身份。

```powershell
$w = "C:\edge-work\run-001"
$mnn = "待替换：MNN Git仓库路径"
$ndk = "待替换：英文路径的android-ndk-r30"
$cmake = "待替换：cmake.exe"
$ninja = "待替换：ninja.exe"
$kleidi = "待替换：v1.16.0.tar.gz"
$adb = "待替换：adb.exe"
$serial = "待替换：当前已配对目标手机的ADB serial"
$env:PYTHONUTF8 = "1"
function Sha($p) { (Get-FileHash -LiteralPath $p -Algorithm SHA256).Hash.ToLower() }
function Real($p) { python -c "from pathlib import Path; import sys; print(Path(sys.argv[1]).resolve(strict=True))" $p }
function Check-Step { if ($LASTEXITCODE -ne 0) { throw "上一步失败，请保留记录并停止。" } }

python scripts/android/build_mnn_source.py prepare --mnn-source $mnn --ndk $ndk --cmake $cmake --ninja $ninja --kleidiai-archive $kleidi --output "$w\artifacts" --records "$w\build-records" --jobs 4
Check-Step
$prepared = "$w\build-records\prepared.json"
python scripts/android/build_mnn_source.py build --prepared $prepared --expected-sha256 (Sha $prepared)
Check-Step
$built = "$w\build-records\build.json"
$plan = Get-Content -LiteralPath $prepared -Raw | ConvertFrom-Json
$buildInfo = Get-Content -LiteralPath $built -Raw | ConvertFrom-Json
python scripts/android/phone_source_candidate.py prepare --manifest $built --expected-sha256 (Sha $built) --binary (Real $buildInfo.binary_path) --library (Real $buildInfo.library_path) --worker (Real "$($plan.worker_directory)\phone_chat_plan_worker.cpp") --helper (Real "$($plan.worker_directory)\prefill_trunk_reuse.hpp") --output "$w\candidate"
Check-Step
$candidate = "$w\candidate\candidate.json"
$llvm = "$ndk\toolchains\llvm\prebuilt\windows-x86_64\bin"
python scripts/android/phone_source_build_audit.py --prepared $prepared --expected-prepared-sha256 (Sha $prepared) --build $built --expected-build-sha256 (Sha $built) --candidate $candidate --expected-candidate-sha256 (Sha $candidate) --llvm-ar "$llvm\llvm-ar.exe" --expected-llvm-ar-sha256 (Sha "$llvm\llvm-ar.exe") --llvm-readelf "$llvm\llvm-readelf.exe" --expected-llvm-readelf-sha256 (Sha "$llvm\llvm-readelf.exe") --output "$w\audit"
Check-Step
$reference = "configs\android\candidate-reference-mi11-qwen3-06b.json"
$referenceSha = "c8236e64cdddaf7fbea8e70503d6a5b82d7174496cd380fec56a8a1f2f348c3b"
New-Item -ItemType Directory -Path "$w\client-temp" -ErrorAction Stop | Out-Null
$env:TEMP = "$w\client-temp"
$env:TMP = "$w\client-temp"
python scripts/android/phone_candidate_validation_collect.py --candidate $candidate --expected-candidate-sha256 (Sha $candidate) --reference $reference --expected-reference-sha256 $referenceSha --output "$w\device" --adb-path $adb --serial $serial --run
Check-Step
$cli = "$w\device\collector-command.json"
python scripts/android/phone_candidate_validation_replay.py seal --run-dir "$w\device\run" --candidate $candidate --expected-candidate-sha256 (Sha $candidate) --reference $reference --expected-reference-sha256 $referenceSha --cli-command $cli --expected-cli-command-sha256 (Sha $cli) --output "$w\device-sealed"
Check-Step
$deviceRoot = "$w\device-sealed\receipt.json"
python scripts/android/phone_candidate_validation_replay.py replay --receipt $deviceRoot --expected-receipt-sha256 (Sha $deviceRoot) --output "$w\device-replayed"
Check-Step
$buildRoot = "$w\audit\receipt.json"
python scripts/android/phone_candidate_chat.py --candidate $candidate --expected-candidate-sha256 (Sha $candidate) --build-audit-receipt $buildRoot --expected-build-audit-receipt-sha256 (Sha $buildRoot) --device-validation-receipt $deviceRoot --expected-device-validation-receipt-sha256 (Sha $deviceRoot) --reference $reference --expected-reference-sha256 $referenceSha --output "$w\trial" --adb-path $adb --serial $serial --run --prompt "你好，用一句话介绍你自己。"
Check-Step
```

摘要从你实际审定的本次文件计算，不从旧报告复制；该流程固定的是本地输入字节，不是作者认证。任一步失败先停止，不能把失败目录塞回同一命令覆盖。宿主构建失败后，如需保留本轮导出的源码而换全新对象目录，用固定配方的`prepare-retry`；这不是续编旧对象。

例子把worker/helper明确指向本次导出的实编快照，不能只因仓库里的同名文件字节一样，就把位置混用。如果编译路径用了junction，构建原件保留当时路径；候选四资产则使用真实解析路径，不改构建回执。客户端TEMP/TMP只在当前PowerShell进程设置到本轮英文目录，不改系统设置。不同硬件、模型和参考须另做明确配置与验收；这里不能直接解除固定设备约束。

本机收尾时曾遇ADB后台启动写`adb.log`被拒；已用本机`adb help`列出的`server nodaemon`前台方式恢复电脑服务，未改权限或手机设置。服务恢复后设备列表为空、旧地址拒绝连接，才能判定当前没有可用连接。不要把电脑服务失败、设备不在线、推理失败混成一种“模型没输出”；前两次未连接阶段没有发送聊天问题；第三次自动发现并核对手机身份后，新候选单题成功，失败原件仍保留。

## 独立宿主构建与手机验证分别证明什么

Android ARM64程序不必在Android上编译。这里Windows运行NDK编译器，输出给Android ARM64执行；因此云上的Windows虚拟机也能检验构建链，但不会替代手机执行模型。构建没有用到模型权重，不需要上传你的模型。

| 检查 | 输入和输出 | 能回答的问题 |
| --- | --- | --- |
| Python离线回归 | 合成协议/配置输入→断言结果 | 客户端规则和失败处理是否符合约定 |
| 独立宿主完整构建 | 公开源码、固定补丁和明确工具依赖→新静态库与worker | 除了作者电脑，构建链能否在独立环境完成 |
| 新产物手机验证 | 这份具体worker、模型、固定题→真实token/文字与清理原件 | 这个产物在该设备和场景是否正常 |

三者应相互补充，不能互相代替。前面的新94程序已经在本机完整构建并通过固定手机三题、单题与连续对话；未来云构建若产生新SHA，只能记为新候选，不能继承新94的手机记录。编译路径和工具不同，尤其带调试信息时，产物SHA不同也不自动表示输出错误。

本轮新增的托管构建入口仍在实现和核验；尚未发生独立宿主完整编译，不能把workflow文件、依赖URL可访问或prepare成功写成构建通过。构建结果和公开运行链接会在实际执行后补充。
