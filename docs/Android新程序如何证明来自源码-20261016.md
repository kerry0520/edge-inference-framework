# 新程序怎样证明来自这份源码

这一节只理解一件事：**源码到程序的构建证据，与程序到答案的运行证据，要接在同一个程序上。**

## 构建在推理主线的什么位置

手机回答问题之前，必须先有能执行的程序。C++源码经过编译生成对象文件，多个框架对象打包成静态库，最后与请求处理worker链接成Android ARM64程序。这个程序在运行时才加载模型权重，执行tokenizer、prefill/decode和底层算子。编译框架不等于训练模型，也不重新量化权重。

## 为什么不能只看“编译成功”

如果链接时误用了旧静态库，你修改的CPUAttention.cpp可能根本没进入最终程序。因此要核对编译命令确实针对当前源码，归档含对应对象，链接命令使用本轮静态库，最终部署的文件就是这个新程序。这些检查回答程序从哪里来，不回答模型结果是否正确。

反过来，只看到手机回答正常，也不能证明当前源码修改已经进入手机；它可能仍在运行旧程序。故部署后还要固定远端程序身份，再发真实请求。请求结束后核输入/输出与执行路径，并确认资源释放，才形成完整链。

## 重新编译后摘要不同意味着什么

摘要不同说明文件字节不同，不直接说明算法或模型不同。例如调试信息里的构建路径就可能改变程序字节。这一轮保持源码修改、编译选项和模型不变，换新的构建目录，目的是检查公开配方能否独立走完，不是宣称又有一项模型优化。

## 当前工程范围

本轮按公开prepare准备全新源码，在保留宿主路径写入失败后，使用公开prepare-retry只复用固定输入，另起空对象目录完整编译；现代构建记录已经通过候选入口接上实机验证。固定手机本轮已确认在线；新程序完成565对象全量编译、归档和链接；固定手机三题的token、文字和预期执行路径与参考一致，模型文件前后未变，退出清理正常。最终独立审核状态以阶段原件（本地原件：`results/android/fresh-candidate-acceptance-20261016/阶段续做.md`）为准。不会把已有程序的上一轮验证挪用为新程序结果，也不自动放开正式运行包。

源码入口按职责看：`scripts/android/build_mnn_source.py`的`prepare()/build()`负责构建；`scripts/android/phone_source_candidate.py`固定交接文件；`scripts/android/phone_candidate_validation.py`的`execute()`安排有限设备请求。无需记这些脚本的审核字段，先把构建与推理的输入输出分清。
