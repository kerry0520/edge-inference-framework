# 构建审查：从“通过”回到实际文件

这项能力为后续新构建试用补前置证据，不是模型优化，也不会自动登记新程序。先分清它检查的编译链：MNN源码生成对象文件，对象组成静态库，静态库与worker链接成为手机程序；模型结构、权重和词表仍另外准备。

| 文件或记录 | 用来回答什么 |
|---|---|
| 源码、配置与编译记录 | 这次要求编译哪些实现，命令是否成功 |
| 实际对象与归档成员 | 库里是否对应这批真正生成的对象 |
| 手机程序与ELF检查 | 最后得到什么架构、依赖哪些系统库 |
| 审查原件根清单 | 这份审查结论具体绑定哪组输入和输出 |

只有摘要里一个 `passed`，不能说明上面这些文件相互对应。新清单把审查结论、对象统计、输入绑定，以及四条只读检查命令的原始输出一起固定下来。后续可以重新核对，而不必凭记忆相信旧结论。

## 原审查与重放有何区别

原审查用显式给定、固定SHA的LLVM工具，读取归档成员和ELF信息，共四条只读命令。它不编译，也不运行手机程序。成功后最后写出 `receipt.json`，绑定15份证据文件；外部再保存这份清单的SHA。

重放只用Python：重新读取实际输入、编译数据库、Ninja对象及归档关系，读取清单绑定的原始工具输出，再按同一检查逻辑算出结果。它检查原命令参数、退出码和超时状态，也比较重新算出的对象与资产结果，而不是只看文件摘要或 `passed` 字符串。

重放明确记录“原审查4条工具命令、本次0条”。输出中的回放命令记录注明原件来源，不把旧退出码0冒充本次执行。重放不会生成一份可以冒充新原生检查的根清单。

## 怎样运行

先按[原构建审查入口](离线源码构建审查入口-20261017.md)完成一次真实审查。现有命令参数保持不变，新版成功目录会额外生成 `receipt.json`；旧审查目录不会被偷偷补写。

在确认选中了正确审查后，把根清单SHA另存于目录外。随后可在项目根目录运行，替换实际SHA与路径：

```powershell
python -B scripts/android/phone_source_build_audit_replay.py --receipt "审查目录/receipt.json" --expected-receipt-sha256 "外部保存的清单SHA256" --output "新的重放目录"
```

输出目录必须不存在，不能覆盖旧证据或与受查输入重叠。失败原件保留，再次验证用新目录。原构建输入和工具文件仍须存在，因为重放会核它们的实际字节；它不是把整个源码、工具链和库打进一个小JSON包。

已有记录中的目录别名按原规则解析并核对同一目标，不因新增重放就破坏旧构建。新清单入口与输出路径仍检查链接和重解析点。

## 类型也属于证据契约

Python中 `False == 0`、`4.0 == 4` 都成立，但“没有发生某事”与“实际整数退出码0”不是同一个字段含义。因此比较重算结果时要保留JSON类型，不能让布尔值或浮点数冒充整数。这个问题不要求你学习额外框架；它说明检查工具也需要能拒绝错误记录的测试。

## 通过能证明什么

通过说明当前输入与指定的原始记录仍能产生相同的检查结论。外部SHA固定字节，不认证作者身份；原始记录本身也不是独立第三方事实证明。不能据此说模型回答正确、手机当前在线、性能提高或任意新构建已可正式运行。

本轮实际审查、重放、负例及未验证范围见阶段记录（本地工程原件）。学习时只需理解编译链与证据链的对应，不必背字段。手机计算主线继续看[项目自学手册](项目自学与独立演示手册-20261017.md)。
