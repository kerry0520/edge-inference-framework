# 受审程序怎样进入聊天入口

本节理解一个主要抽象：**运行包是应用选择并加载程序的交付单位。**它把验过的程序和身份说明放在一起，让聊天入口不用依赖作者的历史构建目录。

## 包负责什么

上一步输出的是新编译的可执行程序，以及说明它来源和验证范围的证据。本步从明确受审的一组证据中选择程序，导出为一个独立目录。目录含程序、少量源码身份文件、profile与来源描述；不打包模型权重、静态库、编译器或ADB。

静态库在链接时已经参与生成程序，运行时不用再加载这份.a文件。模型则是推理时要读取的权重和结构数据，仍保存在手机。所以“导出运行包”不会再次量化模型，也不会复制手机模型回电脑。

## 它与聊天的关系

正式聊天入口读profile，核对包里的文件，部署指定程序；手机进程随后读取现有模型、报告ready，再接收文字请求。后面的Tokenizer、prefill/decode、图执行和CPU算子主线都保持。运行包解决启动前“使用哪一个程序”的问题，不替代推理计算。

例如把包从一个目录搬到另一个目录，程序字节不变，包内相对路径仍能找到它，应用就不应回原编译目录寻找旧库。这正是独立客户端需要验证的内容。

## 为什么不是把candidate的pending改成accepted

候选清单是先前实验的固定输入，不能改写历史记录。正式入口另有明确受审身份：构建证据和手机验证对应这份程序，才能列入本轮可导出的固定包。随手写一份accepted=true，或者给文件重算SHA，不能产生这些证据。

本轮只新增一个明确受审程序的包身份，保留旧包兼容，不声称任意新构建都能自动纳入。日常用户选导出的profile启动聊天即可，不需要记住构建日志或摘要字段。

当前工程与验证范围见阶段记录（本地原件：`results/android/fresh-runtime-delivery-20261017/阶段续做.md`）。源码职责入口：phone_plan_profile.py负责导出和包校验，phone_chat.py选择正式会话，phone_chat_plan.py把包内程序交给既有加载与请求链。

## 本机启动入口

本轮包已导出到下面路径。实机正式入口验收结果见阶段记录；日常聊天仍用默认64个新token，不受验证场景只生成4token的限制。

```powershell
python scripts/android/phone_chat.py --mode full --stats --prefill-plan-cache --plan-profile "build/fresh-runtime-client-20261017/runtime/手机运行包 空格/profile.json"
```

需要手机与电脑连接可用。公开仓库不分发这个程序文件或模型；export-fresh目前只接受本次固定受审记录与对应资产；读者在别处重建得到不同程序时，仍需自己的构建和设备审查并另行纳入。不能仅下载一份profile空壳启动，也不能把公开仓库当作自动验收任意构建的工具。

本轮工程已完成：新包导出后由同机独立客户端通过正式聊天入口完成三题，输出、执行路径与退出清理独立核验；Python文件打开尝试中未见原工程脚本或历史构建读取。旧包兼容回归通过。独立目录验证不等于新电脑验证，本轮也没有新增提速或完整logits结论。
