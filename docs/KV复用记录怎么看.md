# KV复用记录怎么看

这里学习的是“证据能说明哪一种状态”，先不改KV算法。输入是一份已经保存的Session JSON；输出是独立摘要，不连接手机、不重新发题、不改变会话。材料已提供不代表已经掌握。

## 先问有没有启用跨轮复用

当前统一选择的0.6B和1.7B组合都是完整历史重算：每轮保存消息，重新计算完整模板输入；一次decode内部仍正常使用KV。旧的显式`--mode kv`才是固定32-token块的跨轮复用路径。不能看到回答“记住了上一轮”就判定用了跨轮KV，因为完整消息历史也能提供上下文。

日志明确写`full_recompute`，且完整输入数与实际prefill数一致，摘要才列`cross_turn_reuse_disabled`。不认识的策略标未观测；仅仅`reused_tokens=0`不能推出策略关闭。

## 复用了多少和为什么没复用是两件事

例如记录完整输入为143 token、实际prefill47、复用96，则满足143=47+96。固定32块路径还核96对齐32且不超过旧逻辑序列范围。该请求已由客户端列入成功提交、final身份和计数一致，摘要列`positive_reuse`。

如果143个token全都重新prefill，复用0，可能因为没有旧上下文、匹配前缀不足一块、执行资格不满足，或其它引擎决策。现有普通final没有精确原因，摘要写`zero_reuse_reason_unobserved`。它不能靠猜测生成“前缀失配”结论，也不能证明每层KV内容正确。

固定32块路径已校验复用数是32的倍数且不超过`before_all_seq`。例如记录上限为29时，摘要的`recorded_bound_has_no_full_block`为true，表示按记录约束不可能复用完整块。这不是引擎具体分支或已forward前缀的证明；32及以上为false只表示上限不排除复用，其他策略为null。

本次完整`full_input_ids`只说明本次模板输入是什么；它不是“上一题已forward过的token前缀”快照。生成出的EOS也未必进入过下一次forward。这部分需要引擎实际决策点的独立证据，当前摘要一律标`computed_prefix_verified=false`。

## 拒绝、new和未知请求不能算成命中失败

- **预算拒绝：**真实拒绝帧说明输入加生成预留超出部署预算；原记录把它放在拒绝列表、没有同ID成功提交。摘要将它单列，不作为cache miss。它没有重新证明完整历史前后逐项一致。
- **显式new：**确认帧中的消息数和四项Context重置计数为零，说明接口确认了重置；不证明每层内存已释放。只有严格时间顺序可判定时，摘要旁列其后第一份符合条件的已提交请求与前一个new索引；仍不声称知道引擎reset原因。
- **pending/未知结果：**请求可能已经发到手机，但客户端没确认完整结果。它不能归入成功，也不能从残留final帧猜成功，更不能因摘要方便而重发。新对话重置本身未知也单独标出。

摘要的事件按原容器分组，不是复原完整全局时序。时间缺失、相等或非单调时保留诊断，不强行关联new和请求。

## 怎样使用

在项目根目录，用明确文件路径和一个全新的输出目录：

```powershell
python scripts/android/summarize_phone_kv_record.py "某次会话/session.json" --output-dir "results/kv-summary-new"
```

输出`summary.json`和`report.md`；已有输出目录会被拒绝。输入文件SHA在读取前后核对，原文件不修改。身份、计数或成功/未知列表明显矛盾时退出1，不将损坏记录汇总成正常结果。

这是已有记录的解释工具，不是新推理验收器：不会重放原始TCP流，也不证明worker退出、native KV正确、手机当前在线、收益或上游bug已修复。未知字段仍需回看原件。
