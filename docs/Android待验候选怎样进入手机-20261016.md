# 待验候选怎样进入手机验证

上一节的候选清单只固定了文件。本节把这些文件交给一个独立的实验入口，检查手机是否按预期加载、计算并退出；正式聊天入口仍只接受原有已验profile。

## 从文件身份走到一次计算

启动前，先复检候选清单及程序、库、源码，并固定参考记录。部署后核对真正上传的程序摘要，手机加载模型并报告ready；然后才发送消息，让Tokenizer、prefill/decode和MNN执行图真正运行。

实验入口还拒绝记录中明确失败的构建退出声明，避免误选失败产物；这项前置门槛不等于它重新认证了完整编译过程。

“ready了”只说明模型进程准备好。请求返回后，还要核对完整输入token、输出token、文字字节、结束状态和实际执行路径。最后确认模型进程退出、执行计划释放、自有转发移除，才把这次有限验证闭合。

## 三次请求分别回答什么

- 短输入：只有一块，应直接运行完整图。
- 首次长输入：非末块走主干，并首次准备执行计划。
- 清空消息后重复长输入：输入和输出应相同，但计划应命中；消息清空与执行计划释放是不同操作。

每题最多生成4token，是为了控制验证范围，不用它评价回答质量。与旧记录的生成轨迹一致，也不等于比较过完整词表分数。

## 为什么通过后仍不自动成为正式版本

有限的几道题只能证明这些输入和配置下的行为。这次结果不会改写candidate的pending，也不会把它加入正式白名单。编译来源、更多边界输入、完整数值或其他设备仍需要各自的证据；本轮真实候选还是已有2cc程序，不能据此宣布任意新编程序已验证。

候选清单是固定的交接输入，实际运行次数和结果写在新的实验报告里。清单原来的“交接工具没有执行程序”计数不随实验改写，否则它的SHA也会变化，失去绑定本次输入的作用。

本轮已在固定手机运行1个进程、3次请求，覆盖上述三条路径，输入输出与参考一致，退出清理完成。这里只生成4token验证轨迹，短题会截成“2 + 1”，不能拿这个片段评价算术答对与否。最终原件审核见阶段记录。工程原件见阶段记录（本地原件：`results/android/candidate-device-validation-20261016/阶段续做.md`），理解待反馈。

## 这次应理解的重点：清空对话为什么还能复用计划

消息记录、KV和执行计划保存的是三种东西。消息记录是“聊过什么”；KV是“这些token算过什么”；执行计划是“给定形状的张量接下来怎样走图、用哪些执行对象”。新对话应丢弃旧语境，不能把上一题KV当作当前输入；但相同形状仍可能使用同一个执行计划。

例如两次独立提交同一长问题：第二次依然要做模型计算，不能直接把上次答案拿来。它能省下的是适用图的准备工作。因而验证既要看第二次有没有命中计划，也要看输入token、输出token和文字是否仍与独立计算的参考相同。只看“命中”不能证明答案正确；只看答案相同也不能证明走了预期路径。

沿源码只看三处即可：`phone_candidate_validation.py`的`execute()`安排三题与两次`new()`；`phone_chat_session.py`的`new()`处理新对话；`phone_chat_plan.py`的`ask()`检查计划路径。底层仍走已学过的LLM→Module→Session/Pipeline→Backend/Execution链，实验入口负责安排与核验，不代替CPU算子。

本节不要求记住审核脚本、摘要或目录名。希望你能说清楚：**第二次长请求复用的是怎样执行的准备，实际token计算仍会发生。**目前只标为已提供讲解，尚未确认理解。
