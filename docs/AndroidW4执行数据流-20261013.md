# Android W4 执行数据流（2026-10-13）

状态：源码契约与本轮手机观察均已完成独立核验。已讲解，理解待反馈；不将工程通过标为学习者已经掌握。

## 这一课希望你理解什么

Q 投影输入还是一组浮点特征，输出也是浮点特征。W4 内核在两者之间临时把输入变成 int8，把压缩权重拆成可乘的整数，计算后恢复浮点。**一个量化 block 是一段共享权重尺度的输入通道；不同 block 的整数结果必须先回到同一个浮点单位，才能相加。**

以前 nano-vLLM 的分页 block 划分 KV 缓存的存储位置；这里的量化 block 沿一个输出通道的输入维度划分权重。名字相同，职责不同。

## 先把整个算子连起来

当前 Q 图算子把每个位置的 1024 个输入特征变成 2048 个输出特征。把多个位置排成行，数学形式就是 `X × Wᵀ`。相邻 Raster 准备 MNN 需要的布局；Dense Execution 准备和调度计算；本次已确认调用的 `ARMV82_w4_Unit_FP16` 内核完成整数点积与恢复浮点；下一个 Raster 把结果交给后面的 Q norm/attention。

这不意味着本节在重新实现整个框架。我们是在弄清框架的一个真实执行环节为什么能使用压缩权重，并为后续优化找到可靠边界。

|步骤|输入|输出|为什么需要它|
|---|---|---|---|
|动态量化|本次请求的浮点激活|int8 激活及恢复用的 scale/bias|激活每次变化，不能像固定权重那样提前量化一次|
|准备布局|激活/已准备好的压缩权重|kernel 约定的数据排列|让循环按连续数据计算；1×1 的 im2col 不代表空间卷积的滑窗|
|计算一个权重 block|int8 激活、W4 编码和该 block 的元数据|int32 点积，再恢复为 FP32 的贡献|不同权重 block 可以有不同尺度|
|合并 block|每个 block 的浮点贡献|一个输出通道的 FP32 总和|所有输入通道都属于同一个输出的求和项|
|完成输出|总和、算子 bias|half 输出|交回后续浮点算子；FP16 不是说整数乘加在 half 中完成|

## 为什么 block 不能随便合并

暂时忽略零点，只看尺度。设输入 `x ≈ sx × qx`，权重 block 的 `w ≈ sw × qw`。该 block 的浮点贡献为：

`贡献 = sx × sw × Σ(qx × qw)`。

假设两个 block 的整数点积都是 10，第一块 `sw=0.1`，第二块 `sw=0.01`，共同 `sx=0.2`。它们贡献分别为 0.2 和 0.02，输出为 0.22。把整数结果先加成 20 后只乘第一块尺度得到 0.4，会错。这里先恢复浮点，是因为两个整数 10 的单位不同。

一次完整投影仍然只产生一组输出。量化 block 不增加模型层数，它只是让一行权重不同范围使用更合适的尺度。

## 权重的 block 与输入的 block 是两个设置

权重元数据决定 `mBlockNum`。构造器根据每输出通道的 alpha 数量算出它。`mInputBlockNum` 默认是 1；当 `dynamicQuantOption` 对应输入分块非对称量化选项 2 时，才令它等于权重 block 数。

因此即使权重有多块，输入也可能每个位置只用一份 scale。不能看到 W4 就说“每块输入也独立量化”。`mUseBatchQuan` 则涉及按位置量化，与权重 block 数不是同一个概念。实际哪种方式被采用，需要运行时字段作证。

对称量化的大致做法是找该组输入的 absmax，计算量化倍率 `127/absmax` 和恢复倍率 `absmax/127`，把输入乘量化倍率、舍入成整数。非对称量化根据 min/max 同时准备倍率与偏移。真实实现还有全零/常量等边界处理，不能把演示公式当完整实现。

代码接口中不少参数写成 `float*`，但 FP16 专用函数把数据解释成 half。这是 MNN 的函数表接口约定，不能仅由 C++ 指针拼写判断实际元素占几个字节。

## W4 不只是“拆成 -8 到 7 后直接乘”

实际 ARMV82 W4 FP16 汇编用移位和掩码，从一个字节取得两组 `0..15` 编码，随后做有符号 int8 点积（这些非负编码本身仍可作为 int8）。它没有在这一步把每个编码显式减 8。

为什么仍然能表达负权重？初始化阶段会调整权重恢复偏移：对 W4 使用 `originOffset=-8`，把该偏移折入每个 block 的浮点恢复元数据。于是可以用 `w ≈ sw × u + bw` 表示权重，其中 `u` 是拆出的 0..15，`bw` 已包含相应重心修正。

输入也可以一般地表示成 `x ≈ sx × q + bx`。一个 block 的数学贡献因此是：

`sw × sx × Σ(uq) + bw × sx × Σ(q) + bx × Σ(sw×u+bw)`。

前项是整数 dot 乘两个尺度；中项修正权重偏移；最后一项修正输入偏移。最后一项已经包括两种偏移的交叉项，不要再加一次。对称输入时 `bx=0`，这部分省掉。

MNN 会事先计算权重和，并按所选输入量化方式，把输入偏移修正交给内核，或融合进算子 bias。**这是同一个数学契约的不同安排，不能声称每次请求都执行全部三项独立循环。** `srcKernelSum` 已经含输入恢复 scale，因此不能在使用它时再乘一次 `sx`。

## kernel 的参数分别是什么意思

|参数/资源|职责|
|---|---|
|`src`|本次请求已经量化并排好布局的 int8 激活|
|`weight`|提前排好的 W4 编码，以及每个 block 的 FP32 scale/offset；不是只有纯整数数组|
|`src_depth_quad` / 调用处 `blockL`|当前权重 block 的输入深度单位数；不是整个 1024 的裸元素数|
|`realDstCount`|这次调用处理的位置数，可能是一个 tile 的剩余部分|
|`dst_depth_quad`|这次线程负责的输出通道组数|
|`inputScale` / 可选 `inputBias`|激活恢复到浮点时需要的倍率/偏移|
|`srcKernelSum`|每个 block 的激活整数和乘激活恢复尺度，用于权重偏移修正|
|`weightKernelSum`|已恢复到权重浮点单位的权重和，用于输入偏移修正|
|`accumBuffer`|多个权重 block 的 FP32 中间结果；它不是 int32 点积累加器|
|`biasFloat`|完整输出的算子 bias，可包含预先融合的修正|

汇编先用 `sdot` 累加一个 block 的 int32 结果，再 `scvtf` 转 FP32，乘尺度、补偏移；把这一块与前面块的 FP32 结果相加。最后一个 block 才加算子 bias、转 half、按设置夹紧范围并写回。tile 为 12、8、4、1 等路径是处理位置批量的实现细节，本课无需逐条学指令。

## 和线程调度有什么关系

本次此前观察到的 `Dense.thread_select` 按输出通道分给线程。源码中这条路线先为共享输入准备动态量化与布局，再进入线程区间；每个线程拿相同输入计算自己的一组输出通道。各线程不会把同一个输出的半成品相加，量化 block 合并则发生在每个线程负责的输出内部。

这给后续优化一个具体问题：时间花在共享输入准备，还是各线程的 GEMM？只有测清各部分，才知道该减少转换/复制，还是调整算子计算。当前还不能凭这张流程表认定其中哪部分是瓶颈。

## 这次手机实际怎样执行

Q投影与词表输出层的输入深度都是1024。本轮两者的权重均分16组、输入量化分组数均为1；每权重组对应64个输入分量。这里“输入1组”指一个位置的输入深度方向，不意味着整个问题的所有位置共享唯一scale。

|实际物理输入|本轮输入量化分支|权重组/输入组|输入偏移修正安排|
|---|---|---|---|
|Q处理32、29或17个位置|对称量化|16 / 1|不融合输入bias|
|Q处理1个位置|非对称量化|16 / 1|输入修正融合进bias|
|词表输出层处理1个位置|非对称量化|16 / 1|输入修正融合进bias|

这些是请求内的实际元数据和调用返回记录。逻辑prefill/decode阶段没有直接标记，所以表里按物理形状描述，不把shape代替阶段证据。整数核仍分别精确匹配W4/W8 FP16函数。

同一层的权重格式固定，而这次输入怎么量化、偏移修正放在哪里，是Execution依据配置和本次shape组织的。这正是推理框架的职责：把模型数学操作变成能在当前设备上执行的布局、参数和函数调用。

还可以区分两种“分块”：权重16组沿输入深度切，16段贡献最终合成同一个输出；线程按输出通道切，分别得到不同输出，互不把输出半成品求和。实际第一份Q记录的线程分界是[0,103,155,207,256]，单位是8个输出通道，共覆盖2048个输出；分工并非均分。无需背这些数，理解输入深度分组与输出通道分工的方向不同即可。

工程结果压缩为一段：新隔离版本只重编1个CPU对象，565库成员中其余564原字节保持；4手机请求、2组回答轨迹一致，22份目标执行记录有请求闭环，量化及GEMM返回均非零，退出/清理完整。独立审核和root复核通过，2种同步改错的记录被拒绝。没有读取数据值、完整logits测量或性能收益结论；生产入口、原库、模型保持。详见[续做与证据](../results/android/w4-execution-contract-20261013/阶段续做.md)。

下一步若优化这条路径，应先区分共享输入准备与GEMM各自的成本。当前已经知道实际调用与参数，但还没有足够证据选择哪一段修改最划算，不能只凭某条整数指令快就宣布完整模型快。
