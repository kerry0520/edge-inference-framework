# 少算一些之后，怎样判断用户真的等得更短

## 希望你理解什么

本课主要概念是优化的总成本。上一轮已经证明，中间prefill块只执行主干可以得到相同结果。本轮不再证明“能不能省”，而是问：准备另一套执行计划的成本，会不会抵消省下来的计算？

这是从框架执行计划走到实际性能的连接。你学过nano-vLLM的分块和缓存，这里只补MNN的具体代价：长请求会临时准备一个hidden_states输出的Module，结束prefill后释放，再进入原来的decode。

## 一次请求里增加和减少了什么

原完整路径逐块执行Transformer及词表层。候选中间块只执行Transformer，最后块仍执行词表层；但是候选要检查图和共享条件、准备主干Module、最后释放它。

假设省掉词表计算节约20毫秒，新准备与释放却增加30毫秒，总请求会多10毫秒。这个例子只是说明因果，不是实机结果。省下的工作量和实际等待减少必须分别验证。

| 观察量 | 包含什么 | 不能直接当成什么 |
| --- | --- | --- |
| 原生response wall | 模型已加载后，从调用response到返回；含实际输入处理、造图、prefill、采样/decode与内存输出流 | 电脑收到首段文字的TTFT、模型加载时间 |
| native prefill | embedding之后的块执行、KV同步和上下文推进；结束在gc之前 | 整段prompt全部处理成本；它不含外层造图 |
| route_check / prepare / release | 图与共享检查、主干计划准备、主干释放三个子区间 | 额外加到wall上的时间；它们本来就在wall里 |
| native decode | 当前MNN生成循环的计时边界，包含流式写入等 | 纯CPU kernel耗时 |

这些计时不能随意相加。例如wall已经包括prepare，再把prepare加到wall，就是把同一段时间算了两遍。各区间边界也不是完美覆盖全部wall，不能用剩余差值随意命名为某个算子的耗时。

## 为什么要分输入长度并交替比较

33个token只有一个中间块可以省词表计算，512个token有十五个。在每次都准备一次主干计划的实现里，固定准备成本对短输入更显眼，对长输入可能更容易摊薄。因此不能把不同长度混成一个平均提升。

本轮分别比较33/128/512个固定ID；每组顺序是关、开、开、关，即ABBA。它让两种路径都出现在较早和较晚的位置，减轻随时间变化的影响，但不能保证温度、频率或其他系统负载完全不影响结果。预热请求单独记录，不混入测量样本。

长输入由固定ID重复构造，用来控制执行规模；它不是512个汉字，也不是对模型回答质量的评测。必须同时核对两侧输入、输出token和结束状态相同，才能比较相同工作条件下的耗时。

## 内存要单独看

为了观察请求中途的内存，采样线程每10毫秒读一次RSS。但这个线程本身也有成本，所以它不参与正式性能对照。

RSS是进程当时驻留内存，包含权重、KV、临时张量、分配器缓存和代码等；不能把候选比基线多的全部RSS直接叫“主干张量大小”。采样最大值只是所看到的峰值，可能漏掉更短的瞬间。

VmHWM是进程启动以来的累计峰值。第二题HWM仍然很高，不代表第二题再次分配了同样多的内存。因此本轮另开基线/候选两个进程，各看冷、暖两次相同请求，保留模型加载后、请求前后及准备完成时的观测。

## 当前进度与源码入口

新隔离库已经去掉逐层诊断，四个自然请求与上一版输入/输出/状态透明门禁通过。性能与独立内存也已采集并核验；计数来自成功forward的轻量记录，不是新的一组head回调测量。完整词表/KV数学验证沿用上一阶段，并由本轮源码审核核对保持。

入口是 `apps/android/prefill_elision_cost_worker.cpp` 的response外层计时，以及隔离 `llm.cpp` 的generate外层检查/准备/释放、成功full/trunk计数。工程证据见[成本阶段续做](../results/android/prefill-elision-cost-20261014/阶段续做.md)。本课已讲解，理解待反馈。

## 这次结果告诉我们什么

本轮按每个ABBA组分别算两次基线的平均用时、两次候选的平均用时，再看四组配对差的中位数。下表的正数表示候选更慢，负数表示更快；输入是合成固定token ID，输出上限8。

| 输入token数 | 原生response配对用时差 | 四组表现 | 当前结论 |
| --- | --- | --- | --- |
| 33 | +3.88 ms | 三组更慢、一组略快 | 省prefill却没有省总等待 |
| 128 | +3.49 ms | 一组快、三组慢，波动明显 | 尚无稳定收益 |
| 512 | −216.78 ms | 四组均快，约省104～337 ms | 本轮配置下有收益 |

512场景的四组配对改善比例中位数为7.53%。如果忽略配对，只比较全部8个基线与8个候选样本各自的中位数，得到4.43%；这是另一种统计口径，不能混用。这里沿用实验前选择的ABBA配对口径，也保留所有原始样本供复查，并不宣称任意请求都快7.53%。

候选每次检查约1毫秒，准备约11～12毫秒，释放约5.5～5.6毫秒。33场景prefill配对节约约12.43毫秒，新增固定成本足以抵消它；512能省十五个中间词表计算，prefill配对节约约244.79毫秒，才能覆盖这笔成本。各项还有其他工作与波动，不把每个毫秒差值都归因于某一行代码。

两个独立内存进程中，候选冷/暖请求的采样峰值RSS分别比基线高约5.68/10.15 MiB；这不是精确主干分配量。进程HWM早在加载阶段达到峰值，本轮不能用它证明内存节省。

因此这次工程判断是：候选可以继续研究长输入收益，当前实现不应不分长度地默认开启。下一步优先研究安全复用已经准备好的主干计划，减少重复准备/释放，再验生命周期和短输入；也可以先把长输入作为显式opt-in场景。现在还没切换默认聊天入口。
