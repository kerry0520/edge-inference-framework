# Android Execution 的准备与并行计算成本

本课希望你理解：优化之前，必须先说清测量的工作范围；并行区域的等待时间和各线程工作时间不能混为一谈。

前一课已经确认输入临时量化、W4权重分组计算、尺度恢复和FP16输出。这次不改量化公式，先观察一次Execution从输入到输出的时间如何分布。

|区间|计时边界|包含什么|
|---|---|---|
|准备|执行入口的起点→并行区域前|初始setup、动态输入量化、打包、输入和等|
|并行计算|提交线程工作之前→全部线程完成后|派发、各线程局部参数与累加缓冲准备、GEMM、等待|
|收尾|并行完成→执行返回前|剩余输出处理和返回准备|

这三个区间不重叠，在同一单调时钟上满足“准备+计算+收尾=记录的执行总区间”。不是把一段CPU kernel测三遍。记录起点之前的Frame匹配、记录终点之后的日志格式化不在其中；这些仍会影响完整请求，所以总区间也不是完全没有探针开销的原版执行时间。

特别注意：输入量化在ocSplitFunction调用之前已经可能发生，若只从该函数入口开始算准备，就会漏掉它。要沿真实源码确认边界，不能根据函数名猜工作都在哪。

四个线程同时各工作1毫秒，用户等待可能接近1毫秒加调度成本；把四份耗时相加得到4毫秒，说它是等待时间，就解释错了。本轮在父执行线程计开始到join完成，因此记录的是并行区域wall时间；它包含线程等待，不能直接叫纯GEMM指令时间。

原版库与隔离观察版本先做回答轨迹对照。同一观察程序再关/开计时，只改变诊断开关；通过后做交错顺序对照，减少先后顺序带来的误导。少量样本只能报告本次观察范围，不足以把开关之间差值称为准确探针税或永久性能差异。

连续两次读单调时钟的探针只用于了解计时数量级。它不能完整模拟缓存、日志、调度和实际执行场景，不从每条记录机械减去一个中位数。正确读法是保留原始计时，说明观察成本和范围限制。

当前状态：隔离构建、14次手机请求与分段审核完成；具体观察及下一候选见下文，尚无优化收益结论。已讲解，理解待反馈。原始进度见[分段成本续做](../results/android/w4-stage-cost-20261013/阶段续做.md)。

## 本轮观测说明该往哪里走

|本轮ABBA分组|准备占该算子所观测总区间|并行计算占比|
|---|---|---|
|词表输出层，两轮分别统计|约2.6%～2.9%|约97.1%～97.4%|
|Q投影，按轮次和物理plane统计|约3.4%～12.8%|约87.2%～96.6%|

这是“该算子所观测区间”的占比，不是整个模型占比。Q的不同形状、不同轮次分开汇总，不能将它们当同一个等价样本直接混在一起。并行区间仍包含调度、线程局部准备、GEMM和等待；本轮不能从这个百分比宣布哪条汇编指令是瓶颈。

现在有了一个有用的取舍：在词表层，前置准备只占很小一段，先把准备步骤改快，能缩短的范围有限；应该优先检查并行计算中的工作量，或者这次词表计算本身是否必要。这里没有证明某个优化已生效，只是把下一步的问题缩窄。

计时开关后的完整请求时间方向并不一致：有些开计时请求更快，有些更慢。因此不能把两者差值直接叫探针开销，也不能说“加日志反而优化了模型”。校准52纳秒只是连续读取时钟的间隔参考，不代表全部记录成本。

## 下一步回到模型执行计划

普通自回归生成的prefill要先处理整个输入，填入所有层KV；首次采样需要最后输入位置的logits。固定源码的分块循环每块都请求完整logits Module，中间结果被下一块替换，第一次AR采样在整段forwardVec返回后读取最终输出。

所以值得验证的候选是：非最后prefill块执行完整Transformer主干并更新KV，省掉词表输出层；最后块与decode仍计算词表分数。它优化的是执行计划中的工作量，属于推理框架主线。

这里必须保留两个职责：每块Attention都要执行以更新KV，不能跳过整个forward；只有最后的词表投影是候选省略部分。另建主干Module也不保证与原Module共享KV，必须核对所有层状态。只删掉读取logits的代码不足以保证既定Session计划不执行head。

本轮仅提出源码候选，没有创建主干执行计划，没有验证跨Module KV共享，也没有完整logits或速度收益。计时记录仍没有直接标注逻辑prefill/decode；源码分析帮助选问题，不能代替下一轮运行证据。详细条件与源码哈希见[词表层源码候选](../results/android/w4-stage-cost-20261013/head-source-review/source-review.md)。
