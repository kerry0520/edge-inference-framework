# 同图同库的decode输出层诊断

实验日期：2026-10-29；交付复核日期：2026-10-30。

在与当前部署相同模型图、静态库和主要配置的隔离runner中，词表输出节点是正式请求32个decode位置上最大的可见算子。结果支持继续检查这一层，尚未产生新提速方案。

| 描述统计 | 结果 |
|---|---:|
| 逐位置head回调时间 / 同轮forward与输出可读同步时间的中位数 | 30.01% |
| head回调时间中位数 | 6.014 ms |
| 同轮forward与输出可读同步时间中位数 | 20.086 ms |
| head为最大可见算子的位置数 | 32 / 32 |

30.01%来自逐位置比值的中位数，不是后两项中位数相除。32个位置来自同一个诊断进程，不是32个独立样本。

## 测了什么

设备为Mi11，Qwen3-0.6B，CPU4/low/chunk32、greedy、无mmap。输入固定32个token ID，生成预算32。参考与诊断各一个进程，每进程预热、正式各一请求；诊断启用debug回调。实际phase沿同库源码的`gen_seq_len > 0`判据，每请求实测1次prefill及32次decode forward。

模型图中的`/lm/lm_head/Linear`以1×1卷积表示，1024输入、151936输出。图的8位量化声明不证明实际Execution、解码后位宽、GEMM函数或ISA；这些仍未观测。

参考与诊断的完整逐forward f32输出逐位一致，生成token、文字、停止状态以及记录的Context/Meta字段一致。没有比较全部KV张量。本地原件验证还检查了head事件唯一、回调闭合、原生退出、资源前后身份和文件回收完整性。

## 结论边界

这是隔离runner的可见算子成本归因。它不经过聊天模板或TCP，不是正式聊天服务的生产速度A/B。forward边界不包含上层embedding、模板、分词和采样，不能把30.01%称为完整请求或完整decode业务占比，更不代表已经获得30%提速。

回调记录和完整logits捕获会产生观测开销。f32复制即使在forward时钟外，仍可能影响后续执行；不能从参考与诊断的耗时差推断生产加速。无info命令没有回调，比较对象仅为可见算子；嵌套GEMM时间没有再加到算子时间上。

下一步先确认这一层实际量化资源、线程分工与所选计算函数，区分可改善的成本，再提出一个可证伪改动。当前证据不能区分访存、反量化和矩阵运算各自占比，不直接复活此前未获稳定收益的预取候选。

模型、ELF、f32、原始会话和详细设备记录不随公开仓库分发。详细原件、失败记录和身份链保留在原工程，本页是限定结果摘要。
