# 候选交接：同一文件为什么返回两个地址

这是一项开发工具兼容性收尾，不是新的模型优化，也不作为理解MNN计算主线的必学课。

## 实际问题

Windows可能给同一个目录保留长名称和8.3短名称。候选生成工具原先按照输入拼写返回 `candidate_path`，复查工具则先解析成规范路径。于是两个工具操作的是同一份文件，返回结果中的地址却不一致；自动交接和结果比较可能因此失败。

本次让生成工具在写完清单后，使用复查工具已有的路径检查函数，再返回规范路径。它仍先拒绝原始路径中的符号链接和目录重解析点；不是先把链接解析掉、再假装从未经过链接。

## 没有改变候选身份

路径回答“从哪里找到文件”，摘要回答“选的是哪些字节”。规范路径不会改变程序、库、源码的摘要，也不把 `candidate_pending` 改成正式运行资格。清单内容、外部SHA校验、逐资产再绑定和拒绝覆盖规则保持原契约。

这两个地址也不能只因字符串相似就被当作同一资产；仍要通过原有的实际文件和摘要检查。本修复不宣称解决并发目录替换攻击，也没有放开任意程序或设备准入。

## 与推理框架的关系

这项工具在手机加载模型之前交接候选。它不会改变文字分词、prefill/decode、图执行、算子或采样。你只需知道为什么“文件位置”和“程序身份”要分开；学习计算主线继续看[项目自学与独立演示手册](项目自学与独立演示手册-20261017.md)。

实现入口为 `scripts/android/phone_source_candidate.py` 的 `prepare` 与 `plain`；`inspect`继续使用同一条路径核对链。实际回归、真实别名能否验证及适用范围以本轮记录（本地工程原件）为准；离线fixture不代表运行了手机模型。
