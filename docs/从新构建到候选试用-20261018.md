# 新构建怎样进入手机试用

你已经知道一次请求会经过 tokenizer、prefill、decode 和输出。现在补的是请求发生之前的一段：**电脑编出的新程序，怎样成为手机这次真正使用的程序？**

## 三个环节分别负责什么

| 环节 | 输入 | 输出 | 负责的问题 |
| --- | --- | --- | --- |
| 构建 | 固定源码、编译配置、依赖 | 库、worker程序及构建记录 | 编出了什么 |
| 候选检查 | 程序、构建证据、限定设备回归证据 | 明确仍待试用的候选绑定 | 文件与已有验证是否对应 |
| 候选试用 | 上述候选、手机、一个新问题 | 新回答与新会话记录 | 这次是否确实启动了这份程序 |

这里没有发明另一套推理循环。候选试用仍复用现有聊天会话：加载模型、接受问题、执行prefill/decode、流式返回、关闭进程。新入口只负责选定程序并把身份关系接好。

## 为什么两类证据必须属于同一候选

假设构建检查的是程序A，设备测试却跑了程序B。两份报告各自通过，也不能据此说A已经在手机上测试过。

因此入口不能仅检查两个“通过”字样，还要重算各自原件，并检查两边指向同一候选清单、同一构建记录、同一worker与库。设备参考还必须对应本次固定模型和配置。这与nano-vLLM中“调度的请求、实际使用的KV块、最后返回的请求ID必须对应”是同一种工程要求：相邻步骤不能接错对象。

## 旧验证为什么不等于本次启动成功

历史设备记录只能说明那一轮保存的证据相互一致。这次可能换了手机，模型文件可能被移动，上传也可能失败。因此试用仍要执行正常的设备身份、模型、部署程序和ready协议检查。

连接失败就保存失败，不把旧回答显示为本次成功，也不自动重发尚未确认的请求。退出时沿用现有会话的定向清理。

## 候选和正式运行包的区别

候选试用允许开发者验证新构建，但记录仍明确`candidate_pending`、`production_admitted: false`。它不会改正式profile的身份表，也不把几道固定题通过扩展成任意模型、任意设备或所有性能指标通过。

你先理解这条责任链即可：**构建负责产物，检查负责对应，试用负责新执行。** CLI字段和摘要只是实现这条关系的工具，不是另一门必须背下来的推理理论。

## 开发者怎样调用

新入口是`phone_candidate_chat.py`，日常使用既有正式运行包时仍用`phone_chat.py`。候选入口需要已有的候选、构建审查根回执、设备验证根回执和固定参考，各自配外部保存的SHA256。不能靠临时手写“通过”文件跳过两次重算。

```powershell
python scripts/android/phone_candidate_chat.py `
  --candidate candidate.json --expected-candidate-sha256 CANDIDATE_SHA `
  --build-audit-receipt build-receipt.json --expected-build-audit-receipt-sha256 BUILD_ROOT_SHA `
  --device-validation-receipt device-receipt.json --expected-device-validation-receipt-sha256 DEVICE_ROOT_SHA `
  --reference reference.json --expected-reference-sha256 REFERENCE_SHA `
  --output results/local-trial-check
```

上面大写值和文件名都须替换，输出目录必须尚不存在、父目录存在。默认离线预检；实际试用时换一个新的输出目录，再加`--run --prompt "你好，用一句话介绍你自己。"`。不传`--prompt`则进入交互，沿用`/new`、`/history`、`/stats`、`/exit`。可以显式传`--adb-path`和当前连接的`--serial`，不要求沿用历史无线端口。

首版固定已有Mi11、模型、CPU配置和512部署token预算。两份历史回执的完整本地输入仍须存在，因此这不是可以独立搬走的客户端包。启动和请求边界会重核输入摘要，包含较大的库和工具文件，有额外电脑I/O开销；不能用这条试用路径的墙钟时间宣称模型性能。

本机已保存固定输入便捷脚本`results/android/candidate-trial-20261018/launch_trial.py`，默认仅预检；可加`--run --prompt "你好，用一句话介绍你自己。"`进行试用。脚本每次新建记录目录，并为子进程建立英文临时目录，避免传输组件的中文路径限制；不改系统环境、不自动重发请求。它依赖本机完整证据，不随公开源码分发私人路径。

## 这次问题在哪一层被计算

电脑上的Python入口不计算模型。它维护对话消息，把消息和生成上限发到手机，接收流式字节并显示。

手机上的`apps/android/phone_chat_plan_worker.cpp`是桥梁：启动时调用`Llm::createLLM`和`load`；收到问题后整理`ChatMessages`，调用`llm->response(messages, &stream, ...)`。真正的模板处理、tokenizer和生成过程进入固定MNN版本的`transformers/llm/engine/src/llm.cpp`。因此“电脑输入文字”不意味着电脑在执行prefill/decode。

生成的文字通过C++输出流进入worker的`ChunkBuffer`，被封装成带请求ID的字节帧，再回到电脑。电脑用增量UTF-8解码拼接文字；一个token或一块网络数据不一定正好是完整汉字。

先记这三层：**Python管理会话，手机worker连接协议与MNN，MNN执行模型。** 新候选入口改变的是启动哪份worker及检查关系，没有搬走模型计算，也没有另写一套生成算法。

## 连续提问为什么要区分“已发送”和“已确认”

本项目保存的是已经确认完成的对话历史。第一次问题完整返回以后，才把用户问题和助手回答一起加入历史。下一次请求携带这组消息，MNN按当前完整历史执行；这里的聊天模式没有复用KV。

如果手机明确返回“输入token加生成预算超过512”，这次问题没有得到回答，不能加入已确认历史。紧接着再问一个短问题时，它应看到拒绝前的历史，而不是那个超长问题。`/new`则清空对话消息；执行计划可以仍在同一worker内复用，因为它保存的是计算安排，不是上一轮对话内容。

网络断开导致结果未知又是另一种情况：不能当作明确拒绝，更不能偷偷重发。这些区分决定应用是否把一次问题误算成两次，以及后面的回答用了哪些上下文。你在nano-vLLM学过的上下文计算仍适用，这里补的是应用怎样确认和保存状态。

## 实机里具体看到了什么

单题输入“你好，用一句话介绍你自己。”，手机返回“你好！我是AI助手，随时为您提供帮助。”。另一轮在同一worker里先问两次相同长问题，中间`/new`，确认清空消息后仍可命中执行计划；再做短问题、跟随问题、一次超预算拒绝、拒绝后的短问题。

最后几次成功请求带入的消息数是1、3、5：第一问只有用户消息；第二问带上上一问和上一答；拒绝后再问，仍只带已确认的两组问答加新问题，那个超长输入没有挤进去。这是对话状态正确的具体证据。

交互回归把生成上限设为4token，用来核固定轨迹和执行路径，所以这些截断输出不是完整答案质量展示。首个单题使用正常更大的上限。全过程复用了已有worker和库，没有新增模型算法、GPU路径或稳定性能提升承诺。
